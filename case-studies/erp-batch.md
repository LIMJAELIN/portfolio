# ERP 배치 — 부분 실패 격리와 재처리

Spring 기반 인사·근태 ERP에서 정기 배치가 여러 처리 대상을 순차적으로 다루는 과정에서, **하나의 실패가 전체 작업에 미치는 영향을 줄이고 실패 대상을 다시 처리할 수 있도록 흐름을 개선한 경험**입니다.

`Java` `Spring Boot` `Spring Scheduler` `Spring Transaction` `MyBatis` `Oracle`

> ※ 회사 경험은 외부 공개 가능한 범위에서 문제와 해결 구조를 일반화해 정리했습니다.

---

## 1. 문제

배치 작업은 여러 회사 또는 여러 처리 대상을 한 번에 순차 처리합니다.

이 구조에서 모든 처리를 하나의 트랜잭션 경계에 두면 한 대상에서 오류가 발생했을 때 앞서 정상 처리된 작업까지 영향을 받을 수 있고, 반대로 예외만 무시하면 어떤 대상이 실패했는지 추적하거나 다시 처리하기 어려워집니다.

따라서 필요한 것은 단순히 "배치가 끝까지 돈다"가 아니라 다음 두 가지였습니다.

- 한 처리 대상의 실패가 다른 정상 대상까지 중단시키지 않을 것
- 실패한 대상은 확인하고 다시 처리할 수 있을 것

---

## 2. 판단 — 처리 단위별로 트랜잭션을 분리

전체 배치를 하나의 긴 트랜잭션으로 유지하기보다, **업무적으로 독립적으로 처리 가능한 단위를 각각 별도 트랜잭션으로 분리**하는 방향을 선택했습니다.

Spring의 `REQUIRES_NEW`를 사용해 각 처리 단위가 독립적인 트랜잭션을 갖도록 구성했습니다.

```text
Scheduler
   │
   ├─ 처리 대상 A → 독립 Transaction → 성공
   │
   ├─ 처리 대상 B → 독립 Transaction → 실패 / rollback
   │
   └─ 처리 대상 C → 독립 Transaction → 성공

전체 배치 결과
→ 성공 대상과 실패 대상을 구분
→ 실패 대상은 이후 재처리 가능
```

이 구조에서는 B가 실패하더라도 A와 C의 정상 처리 결과를 유지할 수 있습니다.

---

## 3. 구현에서 중요했던 점

### 처리 단위의 경계

트랜잭션을 작게 나누는 것 자체보다 **어디까지를 하나의 성공/실패 단위로 볼 것인가**가 중요했습니다.

서로 함께 반영되어야 하는 데이터 변경은 같은 트랜잭션에 두고, 다른 회사나 다른 처리 대상처럼 독립적으로 완료될 수 있는 작업은 별도 트랜잭션으로 분리했습니다.

### 성공과 실패를 별도로 관리

예외 발생 여부만 확인하는 대신 처리 결과를 성공과 실패로 구분해, 배치가 끝난 뒤 어떤 대상이 완료됐고 어떤 대상이 처리되지 않았는지 확인할 수 있도록 했습니다.

### 실패 후에도 다음 대상 처리

한 대상의 예외가 바깥 반복 처리까지 전파되어 전체 배치를 종료하지 않도록, 실패한 단위는 해당 트랜잭션에서 롤백하고 다음 처리 대상으로 진행하는 흐름을 구성했습니다.

---

## 4. 재처리 과정에서 발견한 문제

부분 실패를 격리해도 **실패한 대상을 다음 실행에서 다시 잡지 못하면 복구 가능한 구조라고 보기 어렵습니다.**

실제 배치 흐름을 점검하는 과정에서 기존 집계 데이터가 존재한다는 이유로 일부 대상이 다음 처리 대상에서 제외될 수 있는 조건을 확인했습니다.

이미 데이터가 있다는 사실과 "정상적으로 처리가 완료됐다"는 사실을 동일하게 취급하면, 중간 실패나 불완전한 상태가 재처리에서 빠질 수 있습니다.

그래서 대상 선정 조건을 수정해, 기존 데이터가 있더라도 다시 처리가 필요한 경우에는 다음 배치에서 재처리 대상이 될 수 있도록 보완했습니다.

---

## 5. 왜 전체 롤백을 선택하지 않았는가

전체를 하나의 트랜잭션으로 묶는 방식도 데이터 일관성 측면에서는 단순합니다.

하지만 이 배치는 서로 독립적으로 처리 가능한 대상이 많았기 때문에 한 대상의 오류로 이미 정상 처리 가능한 모든 작업을 취소하고 처음부터 다시 실행하는 비용이 더 컸습니다.

반대로 모든 실패를 무시하고 계속 진행하는 방식은 처리 결과를 신뢰하기 어렵습니다.

따라서 이 경우에는:

- 처리 단위 내부에서는 원자성을 유지하고
- 처리 단위 사이에서는 실패를 격리하며
- 전체 실행 결과에서는 성공/실패를 구분하고
- 실패 대상은 다시 처리할 수 있게 만드는

방식이 더 적합하다고 판단했습니다.

---

## 6. 검증과 한계

처리 결과는 대상별 성공/실패 집계와 실제 데이터 상태를 기준으로 확인했습니다.

다만 이 경험을 자동화된 대규모 배치 테스트나 CI 품질 게이트 운영 경험으로 확대해 표현하지 않습니다. 회사 프로젝트에는 테스트 코드가 존재하지만, 이 사례의 핵심은 **배치의 트랜잭션 경계와 재처리 가능성을 운영 흐름에 맞게 설계한 경험**입니다.

---

## 7. 이 경험에서 얻은 것

처음에는 배치 실패를 "예외를 잡고 다음 작업을 계속하면 되는 문제"로 보기 쉽습니다.

실제로는 다음까지 함께 봐야 했습니다.

- 무엇을 하나의 트랜잭션 단위로 볼 것인가
- 한 단위가 실패했을 때 다른 처리까지 롤백해야 하는가
- 실패 사실을 어떻게 남기고 확인할 것인가
- 다음 실행에서 실패 대상을 실제로 다시 잡을 수 있는가
- 재처리 과정에서 중복 처리가 발생해도 안전한가

이 경험을 통해 **트랜잭션은 단순한 어노테이션 설정이 아니라, 업무상 성공과 실패의 경계를 코드로 표현하는 수단**이라는 점을 체감했습니다.
